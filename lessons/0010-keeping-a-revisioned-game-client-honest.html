Keeping a revisioned game client honest

A responsive interface can feel optimistic without becoming a second rules engine.

Completed slice: Phase 3A React client

The reducer is the snapshot gate

Every HTTP response is a complete PlayerView. The top-level reducer accepts the first valid view, then replaces it only when the incoming revision is strictly greater. An old poll, duplicate response, or out-of-order completion cannot rewind the table. 

if (incoming.revision <= current.revision) {
  return current; // duplicate or stale delivery
}
return incoming;

Interaction projects authority; it does not invent it

A card becomes active only when at least one server-provided legal command names its exact source. Glowing piles are the destinations in those same commands. Dragging outside, cancelling, or choosing any other pile produces no command.

ServerReturns exact legal commands.
ClientMaps source and destination highlights.
ServerValidates the submitted command again.

Failure preserves orientation

A pending-operation gate prevents duplicate mutations. If a request fails, Sonner explains the safe error while the last valid table stays on screen. A stale-revision response triggers a full refresh. After a keyboard play, focus moves to the updated turn heading or completion result so the player immediately receives the new context.

Security boundary: JavaScript stores only the public game ID. Same-origin cookies carry private session authority and are never copied into local storage or request headers by the client.

Retrieve before revealing

Why ignore an equal-revision manual refresh?

It contains no newer durable state. Clearing the pending indicator is useful; replacing the canonical view is unnecessary.

Why keep polling in one hook?

Polling provides Phase 3 parity, but Phase 4 should replace one transport seam with a subscription rather than rewrite the screens.
