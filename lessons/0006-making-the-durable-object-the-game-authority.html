Making the Durable Object the game authority

One game now has one serialized coordinator that owns its canonical engine snapshot, persistence, player identity, and public views.

Completed slice: real-game Durable Object

Authority is layered, not duplicated

The pure engine remains authoritative for Skip-Bo legality and transitions. GameRoomDO adds multiplayer authority: it decides which player may act, loads the current snapshot, invokes resolveCommand, and durably records the result.

Worker Validate HTTP shape and route the game id to one deterministic Durable Object.
Game room Authenticate a server-issued player token, verify turn ownership, then call the pure engine.
Persistence Store the resolved snapshot before replacing the in-memory cache and returning a view.

The stored model and transmitted model differ

RoomState stores the complete GameState, including every hand and the draw deck. The browser-facing GameView is derived for one player. It includes public build piles, discard piles, stock tops and counts, but replaces every opponent hand with null.

Information boundary: hiding cards is a server responsibility. A UI should never receive secret state and merely hide it with CSS. Private next-player draw effects are filtered for the same reason.

Legal commands are also private view data

Only the active player receives exact legal commands. Other players receive an empty list and isYourTurn: false. This gives the upcoming UI everything needed to enable actions without asking it to reconstruct rules from piles.

Persist first, cache second

A successful transition writes the new room snapshot to Durable Object storage before updating #state. If persistence fails, the process does not advertise an in-memory move that cannot survive eviction. A rehydration test creates a fresh room instance over the same storage and observes the next player’s turn.

The Worker stays stateless

The Worker creates cryptographically random public game ids and uses getByName(gameId) for deterministic routing. It validates JSON request shapes and delegates all coordinated state changes to the room. Room creation explicitly initializes storage, so merely addressing an arbitrary id cannot create a persisted room.

Names are labels; tokens are identity

Joining returns an unguessable player token stored with the roster. Private view and command requests authenticate that token inside the Durable Object. Public player names remain useful display labels, but knowing an opponent’s name no longer reveals their hand or grants their turn. Clients send the token in an Authorization: Bearer header so it does not enter URLs, browser history, or routine request logs.

Retrieve before revealing

Why not store game state in the Worker?

Worker instances are stateless and may differ between requests. One Durable Object serializes all commands for one game and owns durable storage.

Why does the DO still call the pure engine?

Multiplayer authority decides who may request a transition; the engine remains the single implementation of what that transition means.

Why derive views on the server?

It prevents hidden hands and deck contents from crossing the trust boundary at all.
