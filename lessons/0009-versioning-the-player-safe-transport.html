Versioning the player-safe transport

A UI refactor is safest when runtime data gets a contract before it gets a new renderer.

Completed slice: shared React contract checkpoint

One schema owns runtime and compile-time meaning

PlayerViewSchema validates untrusted JSON. Its inferred PlayerView type then drives the reducer and fixtures. A field cannot quietly exist in TypeScript while being absent from the runtime boundary. 

unknown JSON
  → PlayerViewSchema.parse(...)
  → PlayerView
  → reducer action
  → React render

Status is a discriminant, not decoration

The waiting, playing, and finished variants encode different legal states. A waiting view cannot name a current player. A finished view must name a winner and cannot contain legal commands. Parsing rejects contradictory combinations before the UI has to guess.

Revision makes a snapshot comparable

Every future view carries a nonnegative integer revision. The durable room will increment it once per successful mutation. Clients can then distinguish new state from duplicate or out-of-order delivery without comparing every card and pile.

Design rule: HTTP remains the command path; WebSockets will distribute complete player-safe snapshots and recovery signals.

Scaffolding can coexist with the product

The custom build copies the playable static client into dist/, then emits the React checkpoint under dist/react/. Wrangler serves that one generated asset tree. This creates a migration seam without replacing working gameplay with an unfinished shell.

Retrieve before revealing

Why not trust the TypeScript type after fetching JSON?

Types disappear at runtime. Only schema parsing can prove that an external response matches the client assumption.

Why send full snapshots instead of WebSocket commands?

Keeping commands on HTTP preserves one mutation path. Complete views also let clients recover from a revision gap without replay logic.
