Skip-Bo Engine · Lesson 0004

Testing the engine through complete games

A deterministic simulator turns many individually correct transitions into one runnable proof that the rules engine can reach a winner.

Completed slice: local whole-game simulation

The simulator is a real engine client

simulateGame(...) does not modify piles directly. On every step it asks getLegalCommands(state) what is possible, chooses one command, and sends that exact command through resolveCommand(...). Runtime invariants still guard both sides of every transition.

Observe Calculate exact legal commands from the canonical snapshot.
Choose Prefer stock, discard, and hand plays, then end the turn by discarding.
Resolve Apply the normal engine transition until a winner or command limit. 
while (!state.isGameOver && commandCount < maxCommands) {
  const command = chooseCommand(state)
  state = resolveCommand(command, state, { random }).nextState
  commandCount++
}

Why deterministic randomness matters twice

The same seeded random function now drives initial deck creation and completed-pile recycling. A seed therefore identifies an entire run, not merely one shuffle. Seed 42 with two five-card stock piles always produces the same winner, command count, and final snapshot.

Debugging payoff: a failing seed is a compact replay handle. The test suite can rerun the exact card order and transition history instead of hoping a random failure appears again.

A policy is not a rule

The simulator’s command chooser is deliberately simple. Its preference for stock cards is strategy; the command list and resolver enforce legality. Keeping those roles separate means a human CLI, bot, or web client can choose differently without duplicating Skip-Bo rules.

Bounded failure is observable

Automated policies can stall even when the engine is correct. A command limit prevents an accidental infinite run, while a separate diagnostic captures a valid nonterminal state with no legal command. Both return the last valid snapshot instead of crashing. Tests can distinguish “the game reached a winner” from each kind of incomplete run.

Run the checkpoint

bun run simulate -- --seed 42 --stock 5 Ada Grace

Change the seed for another reproducible game. Use --stock 30 for the standard two-player stock size and --max to change the command budget.

Retrieve before revealing

Why must the simulator call getLegalCommands?

It keeps legality authoritative in the engine and makes the simulator behave like any future client rather than becoming a second rules implementation.

What does a seed reproduce?

Initial deck placement, later reserve shuffles, command choices, and therefore the complete sequence of resulting snapshots.

Why return a command-limit result instead of throwing?

Reaching the budget is an expected simulation outcome with useful state, not an invalid engine transition.
