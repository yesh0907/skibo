Skip-Bo Engine · Lesson 0002

State invariants as executable contracts

A valid transition is more than a legal command: the snapshot entering and leaving the engine must also represent a possible game.

Completed slice: setup and state invariants

Compile-time shape is not runtime truth

The GameState interface tells TypeScript that buildPiles is an array of number arrays. It cannot prove that there are exactly four piles, that the cards are between zero and twelve, or that a persisted snapshot still follows Skip-Bo rules.

assertValidGameState(state) is the runtime contract. It returns normally only when all selected invariants hold; otherwise it throws before gameplay logic can trust the snapshot.

Construction Validate roster and deal feasibility, build the state, then validate the finished snapshot.
Transition input Reject malformed state before calculating or applying any legal command.
Transition output Validate the copied next state before returning it to persistence or a client. 
assertValidGameState(input)
  → validate exact command
  → copy input
  → apply and resolve command
  → assertValidGameState(output)
  → return canonical snapshot

What is enforced

  • Two through six uniquely named, nonblank players
  • A valid integer current-player index
  • Exactly four shared build piles and four discards per player
  • Hands of at most five cards
  • Integer card values from zero through twelve
  • Unresolved build piles whose physical cards match each position
  • Agreement between isGameOver and empty stock piles

Official setup versus variants

With no override, setup now deals thirty stock cards for two to four players and twenty for five to six players. An explicit positive stock size still supports Mattel’s shorter-game variants, provided the 162-card deck can also deal five hand cards to every player.

Boundary choice: exact deck conservation is not yet an invariant. Structural snapshots used by focused tests and future replay tools may intentionally omit unrelated cards. Card-count conservation can be added later at a stricter persistence or audit boundary.

Canonicalization before terminal state

A winning stock card may also be the twelve that completes a build pile. Previously, the engine marked the game over first and could leave that completed pile unresolved. The transition now resolves and recycles the pile before returning the terminal snapshot. “Game over” changes which actions remain legal; it does not excuse malformed state.

Why validate both sides?

Input validation protects the engine from storage corruption, stale clients, and hand-built fixtures. Output validation protects every downstream consumer from engine bugs. Together they localize failure: an invalid state is detected at the transition that introduced or received it, not several commands later.

Retrieve before revealing

Why is GameState alone insufficient?

TypeScript types disappear at runtime and express broad structure, not rules such as pile count, sequence, or lifecycle consistency.

Why reject a twelve-card build pile in a snapshot?

Twelve completes the pile. A canonical transition must recycle it before exposing or persisting the resulting state.

Why keep the explicit stock-size parameter?

It represents an official short-game variation while the omitted value remains the standard player-count-dependent setup.
