Skip-Bo Engine · Lesson 0001

Legal commands as the engine’s authority

One calculation now answers both “what may the player do?” and “may this submitted command execute?”

Completed slice: exact legal-command calculation

The problem

The engine previously returned the broad actions playCard and discardCard after nearly every command. That did not say which card, source, or destination was legal, and it could disagree with command validation.

The new contract

1. Enumerate Inspect the current player’s hand, stock top, discard tops, and all four build piles.
2. Validate A submitted command must match one exact command in that calculated set before state mutation begins.
3. Derive Broad UI actions are projected from the exact set, so they cannot claim a play exists when none does. 
GameState
  → getLegalCommands(state): Command[]
  → exact membership check
  → apply command to a copied state
  → getLegalCommands(nextState)
  → derive availableActions

Why exact commands matter

A command is a TypeScript discriminated union. Its type field narrows the remaining shape: a play has a destination build pile, while a discard has a destination discard pile. Play sources narrow again into hand, stock, or discard pile variants.

Because legal choices use the same command shape as submitted input, the CLI, a future browser client, bots, and the Durable Object can all consume one domain-level representation. The clients do not need to reproduce Skip-Bo rules.

The rule predicate

cardValue === WILD_CARD ||
cardValue === buildPile.length + 1

Build-pile position determines the next required number. A wild card occupies exactly one position, so a pile [1, wild] expects 3, not any arbitrary number. Completed twelve-card piles are resolved and recycled before another command is returned.

Correctness property: every command returned by getLegalCommands(state) must resolve from that same state, and a terminal state must return no commands and reject execution.

Defensive boundary details

JavaScript’s Array.at(-1) intentionally accesses the last element. That is useful for pile tops but dangerous for user-provided indexes: a negative hand index could appear to select the last card without removing it. Explicit non-negative integer bounds now protect indexed command sources and destinations.

Retrieve before revealing

Why derive availableActions instead of storing it in GameState?

It is a deterministic projection of canonical state. Storing it creates another value that can become stale or contradict the piles.

Why does a wild card after [1, 2] represent 3?

Build piles advance by position from one through twelve. A wild occupies the next position; it does not erase sequence history.

What should the Durable Object validate later?

Player identity and turn ownership belong at the authoritative multiplayer boundary. Card and pile legality stays in this pure engine.
