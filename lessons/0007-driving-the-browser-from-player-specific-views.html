Skip-Bo Web Client · Lesson 0007

Driving the browser from player-specific views

The browser now renders one safe projection of the game and turns the server's exact legal commands into clickable choices.

Completed slice: playable browser table

The view is the client contract

The canonical GameState remains inside the Durable Object. The browser receives a GameView derived for one authenticated player: their own hand, public piles and counts, current turn, and exact legal commands. Opponent hands and draw-deck contents never cross the network boundary.

Project The Durable Object derives one private GameView after authentication.
Render The browser displays that view and highlights only sources present in legalCommands.
Submit Selecting a source reveals exact commands; choosing one sends the command back unchanged. 
selectedSource
  → view.legalCommands.filter(command =>
      sameSource(command.source, selectedSource))
  → action buttons
  → POST /api/games/:gameId/commands
  → room.playCommand(playerToken, command)

The UI does not calculate Skip-Bo rules

A hand card is actionable only when at least one server-provided command names its source index. The action tray then lists each exact destination: a build pile for playCard, or a personal discard pile for discardCard. This source-first interaction is useful UX, but it introduces no second rules implementation.

Correctness boundary: disabling an illegal control is a convenience. The Durable Object and engine still authenticate and validate every submitted command because browser state is untrusted.

One deployment serves UI and API

Cloudflare Static Assets serves index.html, CSS, and the browser module from the same origin as the Worker API. Requests under /api/* run through the Worker first. The client therefore uses relative URLs and needs no cross-origin configuration.

Identity is per tab

A successful join stores the server-issued player token in sessionStorage. Refreshing the tab restores that player's private view, while a second tab can join as a different player. The token travels only in an Authorization: Bearer header.

Polling is a transport, not authority

Each tab currently refreshes its GameView every 2.5 seconds. Commands still use HTTP and the Durable Object still serializes changes. Replacing polling with WebSocket notifications will improve latency, but it will not change the view or command contracts.

Browser checks catch browser failures

Unit checks confirmed the expected HTML, bearer header, session storage, and responsive CSS. A real two-context browser check then created a table, joined a second player, started a short game, selected a card, and inspected desktop and phone layouts. It caught an empty CSS class passed to classList.add, an exception that static artifact checks could not expose.

Retrieve before revealing

Why send exact commands instead of available action names?

A label such as “play card” omits the legal source and destination. Exact commands let the UI render complete valid choices without recreating rule predicates.

Why use session storage instead of local storage?

It survives refresh but stays isolated per tab, which makes two-player testing possible in one browser without sharing one player's token.

What changes when WebSockets arrive?

The server can notify clients immediately after persistence. HTTP remains suitable for commands, and clients still render refreshed player-specific views.
