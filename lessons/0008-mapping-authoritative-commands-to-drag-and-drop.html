Skip-Bo Interaction · Lesson 0008

Mapping authoritative commands to drag and drop

Direct manipulation can feel physical without moving game rules into the browser.

Completed slice: gameplay feedback revision

Legal commands form a drop graph

Each source card already has zero or more exact commands. During a drag, the client filters GameView.legalCommands by source, then maps each result to a spatial destination. A playCard command maps to one build pile; a discardCard command maps to one personal discard pile.

Pointer down Capture the source card and its current exact legal commands.
Pointer move Highlight only destination elements named by those commands.
Pointer up Match the destination back to one command and submit it unchanged.

The interaction is not the authority

Glowing a destination makes the valid move discoverable, but it is not a security check. Browser DOM and JavaScript are controlled by the player. The Durable Object still authenticates the player, verifies turn ownership, and asks the pure engine whether the submitted command is legal against the current snapshot.

Design rule: the server describes valid intent; the client chooses an ergonomic physical gesture for expressing that intent.

Pointer events unify mouse and touch

One pointer lifecycle handles mouse, pen, and touch. After a small movement threshold, the UI creates a visual card ghost, marks legal drop zones, and tracks the destination under the pointer. Polling pauses during the gesture so a background refresh cannot replace the dragged DOM node.

Presentation can derive meaning from position

The canonical wild card remains value 0. Once it is inside a build pile, its effective value is the card's one-based position in that pile. The UI displays that derived number with a WILD label. No extra game state is required because the build-pile invariant already defines the meaning.

Terminal state deserves a mode change

A finished game is not merely another table update. The result overlay blocks the active table, names the winner from currentPlayerName, changes the message for winner and loser, and stops polling. This makes the domain transition visually irreversible.

Public information should look public

The opponent stock top was already included in the safe GameView, but presenting it as small text made it easy to miss. Rendering the actual card with a count badge aligns its visual importance with the player's own stock pile without exposing any hidden card.

Retrieve before revealing

Why not compute valid piles from their visible top cards?

That duplicates engine rules and can drift. Exact legal commands already contain both source and destination.

Why keep command validation after a legal drag?

Another request may change the game before release, and clients are untrusted. Only validation against the authoritative current snapshot can accept the move.

Why derive a wild card's number instead of storing it?

Its build-pile position already determines the number. Storing a second value would create redundant state that could disagree.
