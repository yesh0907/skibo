Skip-Bo Engine · Lesson 0003

Recycling card supplies with deterministic randomness

Correct deck exhaustion depends on representing where cards are now, when they become drawable, and how randomness enters a pure transition.

Completed slice: draw-pile exhaustion

One supply, two lifecycle states

A completed build pile is reusable, but it is not immediately drawable. The engine therefore keeps two explicit supplies: deck contains cards available for the next draw, while completedBuildPiles holds resolved twelve-card sequences until the deck runs out.

Active deck Draw from the end until the hand is full or the deck is empty.
Completed reserve Preserve each resolved build pile unchanged while cards remain in the active deck.
Recycled deck Flatten and shuffle the reserve only when a draw needs more cards. 
while (hand.length < 5) {
  if (deck.length === 0) {
    if (completedBuildPiles.length === 0) break
    deck = shuffle(flatten(completedBuildPiles), random)
    completedBuildPiles = []
  }

  hand.push(deck.pop())
}

Why the boundary is lazy

Immediate recycling would change the meaning and order of the active deck even when it already has enough cards. Lazy recycling preserves that known supply first. Only the draw operation that observes an empty deck converts reserve cards into drawable cards.

State-model lesson: if two groups of identical values have different legal behavior, represent them as different state. The distinction belongs in the model, not in a comment.

Exhaustion is a result, not an exception

The official draw target is five cards, but a small synthetic state or an exhausted game may not contain enough supply. The draw helper now consumes every available card and returns a smaller hand. That keeps the transition total for valid state: scarcity changes the result rather than turning normal game resolution into an error path.

Random outside, determinism inside

Fisher–Yates produces an unbiased in-place shuffle when its random samples are uniform. The engine copies cards before shuffling and takes a random function through resolveCommand. Production uses Math.random; tests inject a fixed function and can assert the exact resulting hand and deck. 

resolveCommand(command, state, {
  random: () => 0.999,
})

This is dependency injection at the smallest useful boundary. Commands and snapshots stay ordinary data, while the one nondeterministic input is explicit and replaceable.

The invariant follows the lifecycle

Every reserved pile must contain exactly twelve physical cards. At each one-based position, the card must either equal that position or be the wild value zero. Copies also deep-copy the reserve so resolving a command cannot mutate the caller’s nested arrays.

A winning stock play still resolves a completed build pile into this reserve. Since game over suppresses the next draw, those cards remain reserved in the terminal snapshot rather than being shuffled for no gameplay purpose.

Retrieve before revealing

Why not append completed piles directly to the deck?

They are reusable but not yet drawable. Mixing them immediately destroys the lifecycle distinction and can alter draws prematurely.

What happens when deck plus reserve cannot fill a hand?

The engine draws every available card, returns the partial hand, and emits an effect only for the number of cards actually drawn.

Why inject a function instead of a pre-shuffled deck?

The engine still exercises its real recycling and Fisher–Yates logic, while tests control the only nondeterministic dependency.
