Hibernating connections, private projections

A shared room can broadcast one revision without ever broadcasting one shared view.

Completed slice: native Durable Object Hibernation WebSockets

The socket carries views, not commands

HTTPAuthenticates and applies revisioned mutations.
StoragePersists the next canonical room revision.
WebSocketDelivers a fresh private projection.

Keeping commands on the existing Worker-to-Durable-Object RPC path avoids a second mutation protocol. The WebSocket accepts no application messages; it only delivers a versioned room.view envelope from the server.

Identity must survive memory eviction

ctx.acceptWebSocket(server)
server.serializeAttachment({ version: 1, playerToken, playerName })

for (const socket of ctx.getWebSockets()) {
  const identity = socket.deserializeAttachment()
  send(projectPlayerView(persistedRoom, identity))
}

Hibernation keeps the network connection alive while the Durable Object's in-memory fields disappear. The serialized attachment is the durable link back to the authenticated player. On every broadcast, the room validates that attachment against current membership before projecting a view.

One revision, many payloads: Alice and Bob receive the same authoritative revision number, but Alice's envelope contains only Alice's hand and Bob's contains only Bob's. Privacy is preserved by projection at send time, not by filtering a shared broadcast afterward.

Reconnect closes the missed-update gap

A disconnected browser keeps its last valid view, retries with capped exponential backoff and jitter, and performs one authenticated HTTP snapshot after every successful connection. A late snapshot or duplicate WebSocket frame cannot roll state backward because the reducer accepts only a strictly newer room revision.

Retrieve the invariants

Why not send one canonical game state to every socket?

Canonical state contains every private hand and player token. Each socket must receive a separately constructed PlayerView for its authenticated identity.

Why refresh over HTTP after the socket reconnects?

WebSocket delivery is not a replay log. The full snapshot closes any gap created while the connection was unavailable; monotonic revisions resolve races between that snapshot and newer live frames.
