Couple the revision to the durable mutation

A revision is trustworthy only when it describes the snapshot that was actually persisted.

Completed slice: revisioned HTTP backend foundation

One accepted command, one durable snapshot

The room builds its next state with revision + 1, writes that whole state once, and only then updates its in-memory cache. Join, start, leave, and legal game commands all follow the same rule. 

authenticate → compare expected revision → validate transition
  → persist { ...nextState, revision: current + 1 }
  → cache persisted state → project PlayerView

Failures leave no phantom history

Reads, stale requests, illegal commands, and failed storage writes do not advance the revision. This means revision n always names a real durable snapshot—not merely an attempted operation.

Correctness invariant: if persistence fails, both the durable state and the in-memory cache remain at the prior revision.

The boundary turns concurrency into a recoverable result

Start and command requests carry expectedRevision. A mismatch returns stale_revision with the current revision, so the client can refresh rather than accidentally applying an intent to a room it did not observe.

Why does join omit expectedRevision?

A joining player has no authenticated player view yet. The Durable Object still serializes accepted joins and assigns each one the next durable revision.
